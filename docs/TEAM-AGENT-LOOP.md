# 团队群 Agent 循环（VS Code 版 OpenClaw）

> 参考实现：[zhayujie/CowAgent](https://github.com/zhayujie/CowAgent)（Agent Harness）、
> [agentscope-ai/AgentTeams](https://github.com/agentscope-ai/AgentTeams)（Matrix 房间里的多 agent 协作）。
> 目标：**一个脑子**同时负责回话、追问、干活，而不是三条管道各管一段。

## 1. 为什么改

现状是「管道」：

```
群消息 → classifyGroupIntent（16 token） → 判 CHAT：无工具、无记忆、400 token 干答
                                        → 判 TASK：完整 agent 循环（有工具、能读代码）
```

同一条消息，能力差一个量级，而分流是一次 16-token 调用完成的。
用户实况：同一个问题，有时给出带行号的核对表，有时只能干答 —— **那不是同一个东西在回答**。

参考实现里没有这一刀：通道只负责收发，**Agent Core 自己决定**这句话该回、该问、还是该做。

## 2. 目标架构（对齐 CowAgent 的分层）

| CowAgent 层 | 本项目对应 |
|---|---|
| Channels | 团队群窗口 + 局域网/中继传输（`lanSync`） |
| Agent Core | 一次 agent 循环（现有 `AgentRunner`，带工具） |
| Memory | 磁盘上的对话历史（`storage`），群里的活固定一条会话 |
| Tools / Skills | 现有工具集 + 技能注册表 |
| Multi-Agent | 每台设备一个 agent，共享同一个群会话上下文 |

**消息流（新）**：

```
群消息（任意来源：本机输入 / 对端 / 手机）
   └─→ 落成一条需求（带 project / repo / assignee）
         └─→ 进同一条持久会话，跑一次 agent 循环
               agent 自己决定：
                 · 只是问 → 在群里简短回答（带依据）
                 · 不确定 → 群里追问
                 · 需要授权 → 群里申请，等甲方回「授权」
                 · 要改代码 → 拆清单、执行、群里报结果
```

## 3. 保留的确定性护栏（不靠模型）

这些是**代码保证**，不是提示词：

- **项目门禁**：任务所属项目与本机不同 → 先追问，不执行；
- **指派门禁**：`assignee` 不是本机 → 只记录不执行，并在群里说一句；
- **跑完回执**：一轮结束必发群消息（成功 `result` / 未完成 `progress`），模型没报也会补；
- **报数**：群里只喊「报数 / 报到 / 点名」→ 不进 agent、不建需求，每台只回自己的序号
  （按设备 id 排序，两台算出来一致；用户 2026-11-25：「报数不是应该报 1、2、3、4 吗」）；
- **状态灯**：群窗口底部按设备显示 agent 状态（绿闪运行中 / 黄闪等确认 / 红异常 / 灰已停止），
  本机由面板上报、对端通过 `agentState` 控制消息上报；状态只是显示，不进群记录、不触发执行，
  也只在变化时广播；
- **提醒条只给摘要**：追问正文默认三行（清掉 markdown 记号），超过 120 字才出现「展开全文」，
  展开最多 40% 高度并自己滚动；
- **附件与图片**：群窗口的附件走普通对话框同一套 `MessageContext`（图片 → 视觉，文本 → 正文）；
  字节通过 `kind: 'asset'` 分片传给其它设备（到齐才落盘），接收方等收齐后把**本机路径**
  交给自己的 agent；agent 生成的图片随结果气泡一起进群；
- **复制一条消息**：`text/plain`（正文 + 附件清单）、`text/html`（正文 + 全部图片）、
  `image/png`（首图）三种格式一次写入，群窗口与主对话框一致；
- **已读回执**：收到甲方发言后在开跑之前回一条 `kind: 'receipt'`（不进群记录、不产生气泡），
  群里在甲方气泡下显示「已读：X、Y」；5 分钟内没有回执显示「等待对方确认收到」——
  甲方因此能区分「没收到」和「收到了但正忙」；
- **新消息打断并合并**：群里的新消息会中止团队任务那一轮（含子进程），提示词带上
  「这条消息打断了上一轮执行」：先看上一轮做到哪 → 合并新要求 → update_todos 更新清单 →
  从当前状态继续，不从头重做；被顶掉的那一轮不再发「等你回答」；
- **授权卡**：群里回「授权/拒绝」结算最近一张；
- **群会话唯一**：群里的活固定一条会话，不再每条新建（权限也不会被重置）；
- **对话轮换（真的会换）**：一条需求跑完、下一条需求进来时归档旧会话并写交接摘要，
  新的需求从干净上下文开始（结论在群记录 / 对齐账本里，不需要把上一条的工具流水再读一遍）。
  同一条需求的追问 / 回答 / 打断续跑**不换** —— 上一轮读过的文件和跑过的命令正是这一轮要用的。
  归档时会**改名**成「团队任务（21:40 归档）」：找会话是按标题精确匹配的，不改名就会把刚归档的
  那条又找回来、解除归档、接着用（2026-11-26 实测：一条会话堆到 299 条消息 / 5.65 亿 tokens /
  32.8 MB，里面留了 76 条「已换一条新的继续」的交接说明）。改判据在 `src/sync/teamRotation.ts`；
- **单轮请求体不随调用次数膨胀**：一次运行动辄几百次工具调用，折完的旧载荷只留一行状态
  （`hardFolded`），只保最近 24 步的结论；活跃工具输出上限从 160 KB 收到 96 KB；
  旧轮次的 `reasoning_content` 不再回传给 DeepSeek（官方规则：上一轮的 CoT 不进入下一轮）。
  实测 552 次工具调用的请求体从 190 KB 降到 140 KB；叠加上面的轮换
  （历史窗口不再带着上一条需求的流水），单轮输入预计少四成左右；
- **群消息不被吞**：本机正在跑任务时，群里来的消息豁免 `pendingSends` 锁 ——
  忙就先停掉上一轮、只执行最新的，最少也要把消息发进群（以前是判忙发生在发群之前，直接丢）。
- **时间线排序**：按本机**到达顺序**（`receivedAt`，单机单调），不是按两端各自的时间戳 ——
  实测两台时钟差 123 ms 就会让「回复」排到「提问」前面；排完再把甲方需求锚定到
  「回应它的乙方发言」之前（需求先在协议层到达、agent 立刻回话，气泡随后才广播过来）。
  手机页、团队群窗口、群记录共用 `sortGroupTimeline()`。
- **阶段闸门（先谈后做）**：每条需求先进入 `negotiate`（只读：工具清单里没有写文件 / 执行命令），
  谈成后 `awaiting-approval`（方案发给甲方等一句确认），甲方确认才进入 `implement`（放开写工具）。
  阶段存在服务层，面板重载不会丢；甲方说「不同意 / 改一下」退回谈判。判定与提示词见 `src/sync/planGate.ts`。
- **自主迭代模式**（设置 `hwchat.team.autonomous` 或命令「切换自主迭代模式」）：谈成且**所有队友都回过话**
  时直接进入执行，不等甲方；谈判阶段的只读不放松，队友没回话也不抢跑。
- **队友消息不丢**：交付不了（本机正在跑）就排队重投 —— 定时 4 秒 + 每轮结束主动 flush。
  2026-11-26 现场：Windows 一台收到 14 条队友消息，全部止步于「面板正忙」且没有重试，
  用户看到的就是「对方秒回了，我这台毫无反应」。
- **可见性只由 @ 决定**：队友的陈述性回复同样交付给 agent（以前靠「正文像不像在提问」过滤），
  要不要动手由 agent 判断；防接龙靠 30 条轮次上限。
- **已读覆盖每一条气泡**：任何人的发言都会回执，气泡下统一显示「已读：X、Y · 未读：Z」。

## 3.1 任务清单的硬规则（写进提示词）
「不达目标不罢休」的前提是清单本身可验收，否则 agent 会自己糊弄自己：

- 每条都是**能被验证的结果**（看得见的界面效果 / 某字段存在 / 某条命令通过），
  禁止「优化一下」「修一下」；
- 每条都必须是**这台机器自己能做完的**；
- **跨平台对齐只要求行为一致**（用户看到的效果一样），不要求逐字一致 ——
  两台代码库本来就不同（语言、框架、目录都不一样），字面一致永远做不到；
  禁止把「逐字一致 / 行数一致 / 文件内容相同 / 比对两份代码差异」写成任务项，
  也禁止为了对齐去读队友那台的仓库或服务器；各自在本机实现，再在群里用「用户能看到的效果」互相对一遍。

## 3.2 谁说这些话（0.10.3）

用户 2026-11-24：「我看到的是程序或者提示词设置好的程序，而不是 agent 的智能输出输入和互相对话沟通」。

- **正文只放 agent 自己写的话**：完成/没完成的回执不再拼「【项目 X】这台做完了…改动文件：a、b」，
  项目 / 用时 / 改动文件 / 是否被停止 → 结构化 `meta`，由界面渲染成小标签；
- **选项不写进正文**：`接着做 / 换个做法 / 让另一台先做` → 结构化 `options`，界面画按钮；
- **两个 agent 的往来**：和群发言合并成**一条按时间排序的时间线**（不再单独压在对话框下半部分），
  回复自动挂 `replyTo`，标签为「队友对话 / 回复队友」；
- **对话有终止条件**：同一主题 10 分钟内超过 `MAX_DIALOGUE_NOTES = 6` 条就停止自动应答，
  改为在群里请甲方定（继续讨论 / 只让一台做 / 先停下）。

## 3.3 身份标识（0.10.3）
- 统一为 `系统类型 · 设备名`，一处计算（`deviceLabel`），群发言/成员/看板/账本/手机页共用；
- 设备名取系统里用户看到的名字（Windows `COMPUTERNAME`、macOS `scutil --get ComputerName`、Linux `/etc/hostname`）；
- 同名设备自动补 IP（没有 IP 就补设备号短码）；
- 身份 id 的种子保持旧格式，改名不换身份（否则两台互相的信任名单会失效）。

## 3.4 谁是甲方、谁是队友、哪些是说给你听的（0.10.4）

用户 2026-11-25：「agent 需要直到对方身份、用户身份，哪些是说给它听的，哪些不是」。

- 群消息带 `to`（说给哪台；空 = 所有人）。甲方的回答填成提问那台。
- **@ 指派**：token 由设备名归一化生成、组内唯一（同名设备补设备号短码）；发送时按
  token → 完整名 → 唯一前缀解析，多台命中就不猜。甲方明确点名了另一台时，这条是
  **新需求**，不是「回答正在等回答的那台」。
- **追问只在「最新一条」时成立**：甲方只要再说过话，旧追问就不再算在等；并且只有
  明确 @ 提问那台、或内容是一句短回答（追问选项 /「接着做」这类），才当回答处理。
  回答消息只带 `to`，不带 `assignee` —— 没点名就不显示「@某台」。
- 提示词有「## 谁在说话」：甲方 / 你 / 队友三方身份 + 判据：
  - `to` 是本机或空 → 处理；
  - `to` 是别的设备 → **只参考**，不执行、不回答、不重跑；
  - 队友之间 → 参考结论，别重复它做过的事。
- 群消息行会标「说给本机 / 说给 macOS · xxx」；广播不带标注。
- 接收端三层判据（`to` → `assignee` → 提问者），不是给自己的只记录。

## 3.5 协议提示词是「潜规则」：模型读到，用户看不到（0.10.13 / 0.10.14）

用户 2026-11-25：「agent 收到的消息文字很长……除了需求原文外，其他的内容根本不需要
显示出来，只要保证它生效就行了，类似 agent 的潜规则」；随后把模型说清楚：

> 「消息来自谁、要遵循什么潜规则，这些是后台**读取每条消息**的时候会执行，但是不显示在
> 消息明文里。类似于你在群里收到消息，脑子里会先处理这条消息是谁发出的、是针对哪个项目的、
> 根据发消息的身份要分别怎么处理，但是看到的原文不变。」

也就是**一次判断、两条通道**：

| 通道 | 装什么 | 谁看 |
|---|---|---|
| **明文**（`displayContent`） | 甲方 / 队友的**原话** | 用户、气泡、列表标题、复制 |
| **后台**（`content`） | 原话 + 身份（谁说的、说给谁）+ 项目/需求号 + 处理规则 | 模型（历史、上下文、请求） |

关键点：**规则不是写死在一处的一次性配置，而是每条消息重新判一遍** —— 同一条正文，
换个发送者、换个项目，处理方式就不同，所以身份与规则跟着消息走（`content` 与消息同存），
存档里一个字节都不少，界面一个字节都不多。

### 三条入口都按这个模型走（0.10.14）

| 消息类型 | 明文 | 后台 |
|---|---|---|
| 群里的需求 | `requirement.detail` / 甲方原话 | `requirementPromptForLocal()`：三方身份、项目与本机目录、群体近期发言、分工、报数、收尾要求 |
| 队友往来（note） | `note.body` | `notePromptForLocal()`：谁发的、要不要在本机动、怎么回 `replyTo` |
| 甲方回答追问 | 原话 | `answerPromptForLocal()`：说话人、说给本机、需求号/项目/本机目录、「接着那条继续、别再重开流程」、收尾规则 |

落地方式（一条链路三个环节，少一个就失效）：

| 环节 | 做法 |
|---|---|
| 发 | `SendOptions.displayText`：换正文**之前**先把原话存下来 |
| 存 | `ChatMessage.displayContent`：`content` 仍是完整提示词 |
| 显 | 界面只读 `displayContent`；对话标题 / 列表预览也用它 |

### 0.10.14：不许「单方面宣布结果」

用户 2026-11-25：「每次我要求群里的 agent 互相沟通、达成一致的方案的时候，就会有 agent
单方面读取并发出结果。我并没有看到沟通，实际上其他 agent 还没有执行完。」

这是**事实问题，不是措辞问题**，所以三道闸都在代码里：

1. **`ask` 真的等回答**（上限 90 秒；同一段时间连问时后续等待缩到 20 秒）：队友的回答直接
   回到模型上下文里，并附「没谈拢就写分歧，别宣布完成」。
2. **收尾降级**：还有问出去的事没被回答 → `outcomePhaseFor()` 判成 `progress` 而不是
   `result`，正文里明写「还在等「X」回话 —— 这条还不是最终结果」。账本同步标 `in_progress`。
3. **回话叫醒**：队友的回答到达时，即使本机当初没在等（那一轮已经收工），也会**重新起一轮**
   去合并结论 —— 否则回答悄悄落库，提问那台永远不知道。

判据只认事实：显式 `replyTo` 对得上，或同一主题下队友回了话。无关进展（别的主题）不会把
「还在等」变假；超过 10 分钟或对方已经不在群里，则按「不再等」处理（否则任务永远交不出结果）。

## 3.6 三个坑（0.10.4 修）

1. **只读执行把 `team_sync` 也收窄掉了** → agent 说「这次会话里没有可用的群消息工具」，
   跑完什么都发不出。沟通不是写操作，`team_sync` 现在在 `ALWAYS_ALLOWED` 里。
2. **回执靠会丢的 id** → 重载后 `groupConversationId` 为空、续跑后 `syncRequirementId` 丢失，
   于是跑完群里一句话没有。现在起跑时记 `groupRun`，回执只看这个标记。
3. 顺带：`normalizePeer` 以前没读 `repo`，对端永远显示「未绑定 GitHub 仓库」，
   项目门禁也因此退化 —— 现已保留。

## 3.7 不收权限，只约束动作（0.4.31）

用户 2026-11-26：「它会发现没有写工具（甚至会说明「本轮没有写文件能力」），为什么要把风险留给我，
不提前处理掉？」随即又纠正了做法：「**不要收权限**，而是约束它们在涉及需要配合的工作时候，
没有统一方案不开工修改文件。」

所以阶段约束**不抽工具**：

| 阶段 | 工具清单 | 写文件 / 执行命令 |
|---|---|---|
| `negotiate` | 完整（写工具都在） | 调用被 `planGateBlockReason()` 当场拒掉，回一句说明 |
| `awaiting-approval` | 完整 | 同上，并告诉它「等甲方确认」 |
| `implement` | 完整 | 放行 |

拒绝文案必须一次说清三件事（这是「提前处理风险」，不是把风险丢给用户）：

1. 这是**流程约束**，不是权限不足、不是工具坏了 —— 写工具还在你手里；
2. 不要索取授权、不要说「本轮没有写文件能力」、不要当成故障汇报；
3. 现在该干什么（谈 → 出方案 `方案待甲方确认`；等确认 → 只等甲方，需要事实就 `team_sync ask`）。

**仍然收工具的唯一一档**：两台当前选的项目不是同一个（`syncReadOnly` + `SYNC_READ_ONLY_PLAYBOOK`）。
那不是流程问题，是**会写到错的目录**，所以照旧拦在工具清单层面，并给出真正的解锁办法（切项目后重发）。

**覆盖范围不止「对端需求」**：群里直接说的话、队友发来的消息，也按当前需求的阶段带着
`syncPlanGate` 走 —— 只要方案还没定，写到磁盘的动作一样被拦。还没有任何需求时不拦（没有可谈的配合工作）。

**续跑也在闸门内**：阶段由 `resolvePlanGate()` 在轮次内部再算一次 —— 「继续执行 / 重试 / 编辑后重发」
是另起的 `send()`，没有调用方阶段，只信入参就等于留了后门。

**阶段必须过得了两关**（0.4.32 复查补的，缺一个功能就是假的）：

1. **落盘**：`phases` 随 `lan-sync.json` 保存，重载 / 重启后「已确认」还在；
2. **过网**：确认 / 要求改的群消息带 `meta.planPhase`，对端收到即落定；
   `parseSyncMessage` 必须保留该字段（第一版只在类型上加、解析器把它丢了）。

**判据进测试**：`planGate.test.ts` 断言 `resolveSyncReadOnly({ phase })` 不再因阶段返回 true、
写工具被拦而读工具放行、拒绝文案含「流程约束 / 不是权限不足 / 写工具还在你手里」。

## 3.8 团队任务对话就地压缩 / 里程碑清缓存（0.4.31）

### 3.8.1 换对话的唯一依据是「换了需求」（0.4.33）

曾经有一条「体量兜底」：消息 ≥ 24 条或 tokens ≥ 4 万就换新对话。它在**没有需求号的轮次**上
（队友消息、群回声）天天命中，30 分钟归档 8 条、每条 3–5 条消息 —— 消息写进了刚新建的那条，
用户看的那条就「没有新消息」（看起来像「对面已读但内容没进来」）。

现在：`shouldRotateTeamConversation` 只在**明确换了需求**（或里程碑清缓存）时返回真。
体量不靠换对话控制，靠 `planTeamCompaction`（85% 压缩）+ 里程碑清空。

### 3.8.2 对端发言一律可见（0.4.33）

`team_sync action=send|ask` 走 note（会进对话），`action=analysis|question|progress|result`
走群发言（以前只画群窗口）。于是「谁用了哪种动作」决定对面能否看见 —— 与操作系统无关。

现在两条路都进对话：`LanSyncBridge.onPeerLine` → `appendPeerLine()`。
三条硬约束：**只追加不跑模型**（群发言不是执行触发器，否则互相接龙）、**按 id 去重**、
**存成 `user` 角色**（存 assistant 会让模型把别人的话当成自己说过的）。

这条对话是只读执行窗口，用户**不能**自己开新对话，所以涨满之后只能自己压：

| 触发 | 动作 | 实现 |
|---|---|---|
| 上下文 ≥ 85% | 已完成任务每条**一句话**（丢过程/文件/命令）；未完成保留目标；只带最近 6 条消息 | `sync/teamCompaction.ts` → `compact` |
| 清单全做完 **且** 正常收尾 **且** 结论已同步到群里 | 下次开跑前整体换新上下文，旧对话末尾留一条 `teamMilestoneNotice`（每项一句话） | `planTeamCompaction` → `reset`，`shouldRotateTeamConversation({ milestoneDone })` |

「同步了」是硬条件：没同步就清缓存，队友那边还在等这份结论，清掉等于让它消失。
里程碑清缓存优先于「同需求不换」，但「打断后接着跑」（`keepFor`）仍然保留上下文。

## 3.9 反复循环调用同一个工具（0.4.34）

现场：287 步 / 267 次 `read_file` 全在同一个 145.9 KB 文件上按行窗口循环。

| 成因 | 机制 | 修法 |
|---|---|---|
| 折叠把工作集折没了 | 钉住只按**路径**（同文件只钉最后一个窗口）+ 预算 64 KB，两个 48 KB 窗口就互相挤掉 → 永远只看得到一个窗口 | 按「最近 6 段」钉住；预算 200 KB；钉住的连硬折叠都不碰；最新一条永远留 |
| 幂等读判定太松 | 读文件没有副作用，第二次拿到逐字节相同结果就已经是空转，却要等第三次 | `read_file` / `list_directory` / `list_files` / `get_diagnostics` / `search_files` 第二次就拦；`run_command` 仍三次；输出变了自动放行 |

判据可执行：`src/test/readLoop.test.ts`。

## 6. 验收标准

- [ ] 群里问「有没有同步功能」→ 群里出现**带依据**的结论（引用具体文件/字段），不是"看起来可以"；
- [ ] 群里发一条需求 → 对话气泡里**只有需求原文**，看不到协议提示词；模型行为不变（仍按分工/报数/收尾规则做）；
- [ ] 甲方回答追问 / 队友回话后继续的那一轮同样如此：明文只有原话，后台仍带着「谁说的、哪条需求、怎么收尾」；
- [ ] 要求「两台先沟通、达成一致再报」时：没等到队友回答之前，群里**不会出现结果**（只有进度 + 在等谁），对方回话后才出结果；
- [ ] 群里说「让 macos 做」→ 只有 mac 执行，Windows 只记录并说一句；
- [ ] 需要授权 → 群里出现请求，回「授权」后继续、回「拒绝」后停下；
- [ ] 一轮结束 → 群里必有结果（成功或未完成），不需要去右侧对话框翻；
- [ ] 只有一条「团队任务」会话，不因每条消息新增；
- [ ] 关掉协作 → 该会话隐藏；重开 → 复用同一条。
